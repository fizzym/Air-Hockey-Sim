Air-Hockey-Sim · architecture overview

How the AI air hockey robot is built

A Core-XY gantry plays air hockey against a human. A camera tracks the puck, a neural-network policy chooses where the mallet should go, and the policy was trained entirely in a custom simulator that models the real table closely enough to transfer zero-shot. This repository holds the simulator and the reinforcement-learning training code.

1The system at a glance

There are two halves. Offline, the policy is trained in simulation. Online, the trained network runs in a real-time loop on the physical table.

Hardware

Core-XY gantry with two belt-driven motors and SPI encoders, controlled by an STM32 "Blue Pill". A 165 F supercapacitor stops supply sag during aggressive moves. The team later rebuilt it on a regulation table with an 80/20 frame.

Vision

Retroreflective tape on the puck, with an LED array placed next to the camera lens, gives a high-contrast image at 100 µs exposure. A multi-view calibration solves marker positions and table warp together. Contour matching keeps tracking the puck while the gantry beam partly covers it.

Real-time loop

Each cycle the laptop waits for a frame, reads the mallet position, runs the network, plans the path and sends a voltage curve to the Blue Pill. It takes 6–7 ms, run at 60 Hz for headroom, on isolated CPU cores.

2Physical models the simulator is built on

The simulator doesn't use a general-purpose physics engine. Its equations were fitted to measurements from the real table, and most of them can be solved exactly, which is what makes it fast.

Mallet: third-order motor model

Motor voltage to mallet position is a third-order transfer function with six fitted constants a1…a3, b1…b3. In Core-XY these decouple into independent x and y systems:

Vx = (2/R)[(a1−b1)x‴ + (a2−b2)x″ + (a3−b3)x′]

Puck: friction + drag ODE

m·ẍ = −f − B·ẋ², fitted to tracked trajectories. It has a closed-form solution, so the puck's position at any time is a formula, with no numerical integration.

Collisions

A 112-parameter network (outputs plus their uncertainty) maps incoming speed and angle to outgoing ones, for wall and mallet hits. Note: in this branch the network loading is commented out, and the simulator uses fixed restitution (0.94 wall, 0.8 mallet).

A mallet move is a three-step voltage pulse

The policy doesn't output raw voltages. Each action is a target position xf and a voltage level MV, turned into a bang-bang profile V(t) = MVu(t) − 2MVu(t−t₁) + MVu(t−t₂). The simulator solves for the switch times t₁ and t₂ (solve_a, update_path), so every commanded path:

  • can be carried out within the motor's voltage limits,
  • never drives the mallet into a wall,
  • has an exact formula for position and velocity at any time (get_pos, get_xp).

3The vectorized simulator

Air_hockey_sim_vectorized.py keeps the state of N games in NumPy arrays and advances all of them together. Within each step, it jumps from one possible collision to the next instead of advancing in tiny fixed increments.

4Training the policy

The training scripts wrap the simulator in a loop driven by camera, mallet-reading and action events, so the agent sees the world with the same delays and noise as on the real table.

The decision problem (SAC version)

Observation, 39 values

  • Puck and opponent-mallet positions from 5 past camera frames (about 8–100 ms old), so the network can work out velocity itself
  • Its own delayed mallet position and velocity
  • Its previous action
  • Its own motor constants a1…b3 (the opponent's are hidden)

Action, 5 values

  • Target position xf (x, y), limited to its own half
  • Voltage level and its x/y split
  • A "keep the current path" probability: on some steps the mallet keeps its plan instead of re-planning

Reward

  • When the puck crosses to the opponent's side, its path is simulated with the opponent held still
  • Reward = A × puck speed: A = 11.5 if it would score past the opponent, 2.5 if it only reaches the goal when the opponent is ignored, 0 otherwise
  • A large penalty for shots under 5 m/s
  • If the shot would miss, the episode ends, but the game keeps running

Opponents and robustness

Opponent pool

Self-play, a defender agent given about 102 ms of extra vision delay, a scripted side-to-side blocker that encourages bank shots, and frozen past models that specialize in straight or bank shots. SAC learns off-policy, so every opponent's experience goes into the main policy's replay buffer.

Domain randomization

Puck tracking noise (white plus spatially correlated Perlin noise), occlusion and missed detections under the beam, noise in mallet position, velocity and executed voltage, motor constants varied ±, puck mass, friction and drag, and camera and mallet delays drawn from measured distributions.

Networks and settings

The policy is an MLP: 39 → 512 → 256 → 128 → 64 → 10 (mean and spread for each action), with LayerNorm and LeakyReLU. The Q-networks have the same shape. γ = 0.98, τ = 0.001, batch 1024, lr 1e-5.

6Running it

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

The requirements pin CPU-only PyTorch and torchrl==0.10.1, the newest torchrl that still provides the BoundedTensorSpec and CompositeSpec names the scripts import. Each training script picks DEVICE automatically. Without a CUDA GPU it runs on the CPU and simulates 64 games in parallel instead of 2048.

Known gaps. The training scripts load from a checkpoints/ folder that isn't in the repo: set load_filepath = None to start fresh, or point it at a file in model_weights/. Simulation_agent_interface.py and Air_hockey_sim_tests.py still expect the older check_state() return value, and the tests call initialize instead of initalize.

Full derivations, calibration and timing details are in the two final reports: first half and second half.
